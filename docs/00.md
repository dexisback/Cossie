# Cossie Project Overview

Cossie is an AI Agent Security Platform. Rather than building an AI assistant, the objective is to build the layer that sits **between** an AI model and the external tools it invokes.

Instead of asking "Can the model call tools?", the project asks "Should the model be allowed to call this tool?" That distinction drives every architectural decision.

```text
User → LLM → Policy Engine → MCP Tools
```

The model may *request* tool execution; the Policy Engine decides whether execution is allowed. The LLM is never trusted to decide what it may do.

## Motivation

Modern LLMs can invoke tools (e.g., `restart_server(server="prod-01")` in response to "Restart production server"). Without guardrails, the tool executes immediately. Uncontrolled tool use enables:

- Deleting production data
- Restarting critical infrastructure
- Leaking secrets
- Prompt injection
- Bypassing system prompts
- Calling expensive APIs indefinitely
- Escaping intended permissions

## Project Goal

The goal is not merely connecting to MCP servers, but building an autonomous agent that can:

1. Discover tools dynamically
2. Reason about which tool to call
3. Request tool execution
4. Have every request inspected by policy
5. Enforce security policies
6. Optionally require human approval
7. Execute tools only if permitted
8. Produce complete audit logs

## What Was Built

The implementation grew beyond the original specification into a small production-grade AI security platform:

| Area | Capabilities |
| --- | --- |
| Core runtime | AI Agent, Tool Loop, MCP Registry, Dynamic Tool Discovery, Chat Service |
| Policy platform | Policy Engine, Rule Evaluation, Rule Priorities, Block / Approval / Risk / Budget / Input Validation rules |
| Synchronization | Redis Pub/Sub hot reload, Rule Cache, Runtime Tool Refresh |
| Security | Prompt Injection Detection, Risk Classification, Risk Overrides, Audit Logging |
| Persistence | Tool Catalog, Approvals, Rules, Risk Overrides, Execution Logs |
| Reliability | Gemini primary with Groq fallback, retries with exponential backoff on the fallback path |

## Intended Users

The application is **not** designed for end users. Its operators are security, platform, AI-infrastructure, and DevOps engineers responsible for governing autonomous AI agents. The dashboard therefore resembles a security operations console rather than a consumer product.

Mental model: *"The LLM may decide what it wants to do. Cossie decides whether it is allowed to do it."*

## High-Level Architecture

```text
        ┌──────────────┐
        │   Dashboard  │  Policies / Approvals / Tools / Logs
        └──────┬───────┘
               │ REST APIs
        ┌──────▼───────┐
        │   Agent API  │
        └──────┬───────┘
               │ user prompt
        ┌──────▼──────────┐
        │ Prompt Security │
        └──────┬──────────┘
        ┌──────▼──────────┐
        │    LLM Layer    │  Gemini → Groq fallback
        └──────┬──────────┘
        ┌──────▼──────────┐
        │    Tool Loop    │
        └──────┬──────────┘
               │ tool request
        ┌──────▼──────────┐
        │  Policy Engine  │
        └──────┬──────────┘
               │ ALLOW / DENY / REQUIRE_APPROVAL
        ┌──────▼──────────┐
        │  MCP Registry   │
        └──┬───────────┬──┘
           │           │
   Custom MCP Server  Remote MCP Server
```

Checks are intentionally placed *outside* the agent loop — the `if(tool == dangerous)` pattern inside agent code was deliberately avoided:

```text
Agent → Policy Engine → Decision → Tool
```

This keeps the policy engine reusable, independently testable, transport-independent, and LLM-independent. The agent does not know how security decisions are made, the policy engine does not know which LLM is used, and the registry does not know why a tool was denied.

## Engineering Principles

1. **Separation of concerns** — each subsystem owns exactly one responsibility: Agent (orchestration), Policy Engine (authorization), Registry (discovery/execution), Dashboard (administration), Redis (synchronization), Database (persistence).
2. **Runtime discovery** — no hardcoded tool lists. Every MCP server is queried at runtime; adding one requires no agent code changes.
3. **Runtime configuration** — policies change without restarting the agent (DB update → Redis publish → rule reload → next request uses new policy).
4. **Policy first** — the model is untrusted: "LLM proposes, policy decides."
5. **Strong module boundaries** — the agent imports the Policy Engine, Registry, and shared types rather than reimplementing them, keeping coupling low.
6. **Security before capability** — when capability and safety conflict, safety wins.

## Monorepo Layout

The project is a monorepo split into reusable packages instead of a single Express app, because different systems evolve independently, multiple apps consume the same packages, shared types eliminate duplicated interfaces, and packages stay independently testable.

```text
apps/
    agent/
    custom-mcp/
    dashboard/

packages/
    db/
    logger/
    mcp-registry/
    policy-engine/
    shared-types/
```

Additional conventions:

- `apps/` holds application entrypoints, `packages/` holds reusable libraries, `generated/` holds generated code only (never business logic).
- Backend services are thin-controller/service-oriented: Approval Service, Tool Loop Service, Chat Service, Rule Loader, Risk Resolver, Log Service. Routes call services; services own behavior.

## Applications

### Agent

The runtime of the system: receives user prompts, communicates with the LLM, executes the tool loop, invokes the policy engine, executes MCP tools, writes audit logs, exposes REST APIs, and orchestrates approvals. It contains minimal business logic and delegates to dedicated modules — it coordinates, it does not implement policies itself.

### Dashboard

An administrative console for configuring the running agent: create/enable/disable rules, inspect tools, override risks, approve requests, inspect logs, monitor MCP servers. It never talks directly to MCP servers — only to the Agent API.

### Custom MCP Server

Designed as a small infrastructure management API exposing tools such as list servers, restart server, deploy release, rollback release, and retrieve logs. It follows the MCP specification properly; the agent contains no special-case code for these tools and discovers them dynamically.

## Packages

| Package | Responsibility |
| --- | --- |
| `shared-types` | Zod schemas, shared interfaces, enums, runtime validation, policy/MCP/tool/risk/approval types. Every package imports these contracts, guaranteeing consistency. |
| `db` | Single Prisma client: Neon connection, Prisma init, WebSocket adapter config, exported instance. No app constructs its own client. |
| `policy-engine` | Isolated from Express, MCP, Gemini, Groq, Prisma, and Redis. Receives a `PolicyRequest`, rules, and context; returns a `PolicyDecision`. Knows nothing about how requests arrived. |
| `mcp-registry` | Abstracts MCP: discovering tools, connecting to servers, refreshing discovery, executing tools, caching results. Hides stdio/SSE transport details from the rest of the app. |
| `logger` | Centralized logging through a common abstraction. |

## Request Lifecycle

Every request follows the same pipeline:

1. User sends prompt via `POST /api/chat`.
2. Prompt Security scans it.
3. LLM produces a response or a function call.
4. On function call: look up the tool → evaluate the Policy Engine → decision (`ALLOW`, `DENY`, or `REQUIRE_APPROVAL`).
5. If allowed: Registry executes on the MCP server.
6. Tool result feeds back into the LLM until the model stops requesting tools, then returns the final response.

The loop iterates until the model responds without a function call. The Tool Loop never makes authorization decisions — those belong exclusively to the Policy Engine.

## Prompt Security Layer

Before reaching the LLM, prompts are scanned heuristically for phrases like "ignore previous instructions", "act as root", "bypass security", "override policy", "jailbreak", "disable guardrails".

Behavior: detection → audit log → conversation continues. Prompts are intentionally **not blocked**, because false positives are common; logging provides visibility without harming legitimate users. Detection is separated from enforcement ("monitor first"), mirroring production security systems. Future versions may make enforcement configurable (monitor / warn / block).

## LLM Layer

Multiple providers are supported for resilience:

- Primary: Gemini (`gemini-2.5-flash`)
- Fallback: Groq (`llama-3.3-70b-versatile`)

Routing strategy: try Gemini → on failure fall back to Groq (Groq calls are retried up to 3 times with exponential backoff). The agent does not know which provider ultimately produced an answer.

## Tool Discovery

"No hardcoded tool lists" is a core requirement. Discovery flow:

1. Register server → connect.
2. Query `tools/list` and receive schemas.
3. Infer risk per tool.
4. Resolve administrator overrides.
5. Persist tools into the Tool Catalog.
6. Cache in the Registry.

Adding an MCP server immediately makes its tools available — including to the dashboard — with zero code changes.

## Registry Cache

The registry keeps an in-memory cache to avoid rediscovering tools on every request. Each entry stores the server configuration, discovered tools, connection state, and last synchronization timestamp. Refreshes overwrite cached tools.

## Tool Catalog

Runtime discovery alone is insufficient: an in-memory-only inventory prevented dashboard browsing, historical tracking, risk overrides, metadata, and analytics. Discovery therefore persists every tool into the `ToolCatalog` table (`Discover → Persist → Cache → Dashboard`), creating a permanent inventory of available capabilities.

## Risk Classification

Each discovered tool receives a heuristic risk level derived from its name and description: patterns like delete/destroy/terminate/shutdown/rollback → `CRITICAL`, restart/deploy/write/update/modify/create → `HIGH`, read/get/search/list/find → `LOW`, everything else → `MEDIUM`. Examples: `list_servers` → LOW, `restart_server` → HIGH, `rollback_release` → CRITICAL. The final runtime pipeline:

```text
Infer risk → database override lookup → final risk
```

The Policy Engine consumes the final risk. Risk describes a *tool*; policy describes *organizational behavior* — separating them lets different companies treat the same CRITICAL tool as block-always, approval-required, or allow.

Risk overrides let administrators disagree with automatic classification (e.g., mark an internal deployment tool LOW despite a HIGH heuristic). The override always wins at runtime.

## Rule Lifecycle and Cache

Rules moved away from hardcoded definitions during development. Current lifecycle:

```text
Dashboard → REST API → Prisma → Redis publish → Rule Loader → Zod validation → Rule cache → Policy Engine
```

- Validated rules are cached in memory so the engine does not query PostgreSQL on every tool call.
- Redis invalidates the cache whenever rules change.
- Every runtime boundary validates input: `Database JSON → Zod validation → engine rule → cache`. Invalid rules never reach the policy engine. This was added after type mismatches between raw DB JSON and engine expectations caused subtle bugs, and became one of the largest architectural improvements.

## Redis Synchronization

Redis exists solely to synchronize runtime state — it is an event bus, not primarily a cache. Without it, policy changes would require an agent restart; with it:

```text
Rule updated → DB write → publish policy:updated → subscriber reloads rules → cache updated → next request uses new rules
```

No restart occurs. If Redis fails, cached rules continue functioning and only live updates stop — an acceptable degradation.

## Approval Workflow

Approvals add a third outcome beyond binary ALLOW/DENY: PAUSE.

```text
Tool request → Policy Engine → Approval required → stored in database → surfaced in dashboard → human approves/rejects → execute (or stop)
```

Execution genuinely pauses rather than logging intent. A pending approval is persistent state (statuses: `PENDING` / `APPROVED` / `REJECTED` / `EXPIRED`; unresolved approvals expire after 30 minutes). When an administrator approves via the API, execution happens immediately at approval time — the stored arguments are executed through the Registry and the result returned in the approval response. This resembles enterprise deployment workflows and was considerably more robust than returning an error.

## Audit Logging

Every important event is logged: tool executions, prompt injections, approval creation/approval/rejection, policy decisions.

Logs record richer structure than just ALLOW/DENY: event type, decision, matched rule, reason, and trace. Decisions and event types are separate concepts (e.g., Decision `ALLOW`, Event `PROMPT_INJECTION`) — this separation makes audit logs far more expressive, queryable, and visualizable. Audit logs answer: what happened, why, who decided, which policy matched, and whether the action can be reproduced.

## Health Endpoint

Originally returned only `OK`; now reports database status, MCP servers, tool counts, and uptime, providing operational visibility.

## Edge Cases

| Scenario | Current behavior | Future improvement |
| --- | --- | --- |
| MCP server crash mid-execution | Execution fails; error propagates | Retry, circuit breaker, health monitoring, automatic reconnection |
| Prompt injection | Detected → audited → conversation continues | Configurable enforcement |
| Conflicting rules (block vs. approval) | First matching rule by priority wins; lower integer = higher precedence; deterministic | — |
| Offline approver | Approval persisted; execution pauses; later approval executes immediately via the approve endpoint | — |
| Database failure | Prisma propagates errors; health endpoint reports status | Read replicas, graceful degradation |
| Redis failure | Cached rules keep working; only live updates stop | — |
| LLM failure | Retries → backoff → Groq fallback | — |

## Design Rationale

**Why the policy engine is the center.** Most AI applications revolve around the model; this project revolves around the Policy Engine. The LLM becomes replaceable while policies remain authoritative. Because the engine is pure, stateless, deterministic, and infrastructure-free, it could be exposed as REST, gRPC, CLI, library, or worker without assuming Express exists. The biggest architectural shift of the project was moving from "how can an LLM use tools?" to "who decides whether the LLM is allowed to use tools?"

**Why configuration lives in the database.** Hardcoded policies mean security changes require deployment and non-developers cannot administer the system. Rules, risk overrides, approvals, and tool metadata are data, not code.

**Why shared types.** Every package depends on contracts from `shared-types`, giving compile-time consistency, runtime validation, documentation, and discoverability; interfaces otherwise drift over time.

**Why Zod alongside TypeScript.** TypeScript validates source code at compile time but cannot validate runtime JSON loaded from the database. Zod protects the runtime boundary.

**Why the registry isolates MCP.** Transport complexity (stdio, SSE, and potentially HTTP, WebSocket, streaming MCP) stays behind the Registry; the rest of the application never changes.

**Why persist the tool catalog.** Discovery is transient; inventory is permanent. Persistence enables browsing, analytics, historical comparison, risk overrides, and reporting.

**Why event types.** A decision and an event are distinct concepts; separating them simplifies querying and visualization.

Code organization evolved from large files → feature folders → packages → services → reusable modules, reducing coupling and increasing configurability at each step.

## System Evolution

```text
Simple Agent → Policy Engine → Dynamic MCP → Rule Persistence → Redis
→ Risk Classification → Approvals → Audit Logs → Prompt Injection
→ Risk Overrides → Runtime Validation → Production-style Architecture
```

Each iteration reduced coupling while increasing configurability, transforming the project from a proof of concept into a configurable runtime system. The final backend is a policy enforcement platform whose AI agent is only one consumer.

## Frontend Vision

The frontend is intentionally **not** a CRUD admin panel — it is an operational security dashboard resembling Linear, Grafana, Datadog, or GitHub rather than a Bootstrap admin template. Every screen answers operational questions: What tools exist? What policies are active? What requests are waiting? What was blocked and why? What did the LLM attempt? How healthy is the system?

Planned navigation (one operational concern per page, no duplication): Overview, Policies, Tool Catalog, Approvals, Audit Logs, MCP Servers, Settings.

UX principles: simple, fast, minimal, information-dense, few clicks, keyboard-friendly, immediate status visibility, emphasized security-critical actions. Visual goals: dark, professional, strong typography, consistent spacing, clarity over animation. Opening the dashboard should convey health, pending approvals, current risks, recent activity, and active policies within seconds.

Intended operator journey: open dashboard → understand platform health → inspect tools → review active policies → investigate suspicious events → approve pending operations.

## FAQ

- **Why separate the Policy Engine?** Authorization should not depend on the transport layer or the LLM provider; a pure engine is easier to test, reuse, and reason about.
- **Why Redis?** Not as a cache — as an event bus propagating policy changes to running agents without restarts.
- **Why dynamic discovery?** Hardcoding tools violates the MCP philosophy; the registry should discover whatever capabilities a compliant MCP server exposes.
- **Why persist discovered tools?** Runtime discovery is ephemeral; persistence enables inventory management, historical tracking, risk overrides, and dashboard visualization.
- **Why Zod if TypeScript exists?** TypeScript validates source code; Zod validates runtime JSON at the DB boundary.
